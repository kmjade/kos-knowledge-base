# KOS-Think：10 原则思维循环

> 一套冥想、一种纪律、一份检查清单。当问题足够复杂时使用——架构决策、事后复盘、模糊需求、多方权衡、"我们漏了什么？"时刻。

10 原则不是菜谱，是注意力的各个阶段。初轮按顺序走，之后根据新信息回环。纪律在于**不要跳过**那些不舒服的阶段（OBSERVE 内部、ACCEPT、GROW）。

---

## 10 原则

### 1. OBSERVE（外部输入）

思维始于数据收集。观察环境、当前格局、模式和低效——不加评判，不急于解决。

**实践：** 改代码前先读代码。回答问题前先读 vault 中的每一页。抗拒在第一个症状就跳到修复的冲动。

### 2. OBSERVE（内部元认知）

现在观察你自己。这是元认知——思考你是如何思考的。你基于假设在操作吗？你对某个架构有偏见吗？你锚定在之前的决定上了吗？

**实践：** 在评分前写一段"偏见日志"。标记所有权偏见、发布偏见、熟悉偏见、锚定。偏见不会因为被指出就消失——它被控制住了。

### 3. LISTEN（主动接收）

观察通常是视觉的或分析的。倾听需要关闭自我以吸收外部反馈。关注用户意图、错误信息、噪音中的微妙信号。

**实践：** 在假设某个技能做什么之前先读它的 SKILL.md 描述。在复述之前先读用户的准确措辞。用户的困惑是数据。

### 4. THINK（批判性处理）

分析引擎。一旦有了输入，把问题分解到第一性原理。结构化逻辑，映射工作流，评估约束，将原始数据综合成连贯策略。

**实践：** 读后再写。命名如下一个读者是敌人。最小可用单元。删比加多。证据胜于直觉。失败即规范。

### 5. CONNECT（横向联想）

伟大的想法很少在真空中发生；它们在交叉点发生。把两个看似无关的概念连接起来。顿悟时刻是发现不同变量之间的隐藏关系。

**实践：** 审计一个技能时问"这个 bug 模式在相邻技能中存在吗？"。横向思维能发现单组件视角错过的跨切面问题。

### 6. CONNECT（系统编排）

第二个 CONNECT 关乎执行。从孤立想法到集成系统。这些个体思想、工具或代理如何相互配合形成一个无缝运作的整体？

**实践：** 交付一个新特性时，审计它如何与文件锁、Delta manifest、日志系统、AGENTS.md 协议集成。在隔离中工作的特性不算工作特性。

### 7. FEEL（同理心 + 直觉）

纯粹的逻辑没有同理心是脆弱的。考虑人的因素。为使用体验设计。

**实践：** 说"ERR: exit code 4"的错误信息通过了 THINK 但没通过 FEEL。用户第一次安装插件时的体验是 `make test` 无法衡量的。

### 8. ACCEPT（智识谦逊）

没有计划能在第一次接触现实时幸存。接受约束。承认假设失败。识别你的技能只有 78/100 时，不要写 95/100。ACCEPT 是防谄媚防火墙。

**实践：** 诚实地评估结果。如果 verdict 是 YELLOW，不要为了取悦任何人叫它 GREEN。

### 9. CREATE（生成输出）

分析瘫痪是进步的敌人。在某个时刻，停止策略制定，开始产出。写代码。起草内容。发布系统。

**实践：** 从未被写出的审计比一个 B+ 级已发布的审计更差。CREATE 是当前面阶段给了你足够信息时的答案。

### 10. GROW（迭代循环）

思维不是一条直线；它是一个反馈循环。用它来升级你的技能，扩大你下一轮的能力。

**实践：** 每个审计必须以 GROW 章节结束。什么有效？下次如何改进？GROW 把一次正确的决定变成复合习惯。

## 何时调用

调用 `/think` 当：

- 你要做非平凡的架构决策（设计新技能、重组模块、方案选型）
- 你在审计一个系统，需要方法论骨干
- 用户的请求是模糊的，你需要先倾听再回应
- 你遇到了出乎意料的结果，需要 OBSERVE(内) 后再调整
- 你正要宣布完成，需要 ACCEPT 检查（防谄媚）
- 某事出问题后的事后复盘
- 关闭会话前做 GROW 步骤

**不要调用** `/think` 当：

- 单行 typo 修复（纪律是过度杀伤）
- 琐碎查询（没有决策在做）
- 你已经潜意识地走过了 10 个阶段（不要仪式性地重做）

## 每阶段提示词

### 1. OBSERVE（外部）
- 原始输入是什么？（代码？文档？用户意图？日志？）
- 我完整读了什么 vs 扫读了什么 vs 假设了什么？
- 当前环境/状态是什么？（工作树、最近提交、KOS 引擎状态）
- 在我开始解释之前，有什么让我意外的？

### 2. OBSERVE（内部）
- 我对什么有偏见？（所有权、发布、新颖性、锚定、熟悉度）
- 我无意识地希望什么结果？为什么？
- 如果一个全新上下文的审核者现在加入，他们会质疑什么我在视为理所当然？
- 我的信心是否校准到了我实际拥有的证据？

### 3. LISTEN
- 用户实际上请求了什么？（逐字引用）
- 噪音中有什么信号？（措辞选择、他们没说什么、之前的修正）
- vault 中的现有页面 / 日志提供了什么上下文？
- 这个决策中谁的声音缺失了？

### 4. THINK
- 涉及的第一性原理是什么？（约束、不变量、爆炸半径）
- 应用六个工程内核：读后再写、敌对命名、最小单位、删比加多、证据胜于直觉、失败即规范
- 我还没考虑过的替代方案是什么？
- 能证明我错了的最便宜的实验是什么？

### 5. CONNECT（横向）
- 这个模式还在哪里出现？
- 什么看似无关的领域解决了结构相似的问题？
- 我们的其它 KOS 引擎（Triage/Compile/Link/Daily）有类似的模式吗？
- 什么隐喻能解锁用户对这个的直觉？

### 6. CONNECT（系统）
- 这如何插入现有的接线？（文件锁？Delta manifest？日志系统？AGENTS.md？）
- 有什么需要在下游/上游/跨系统更新？
- 集成创造了哪些隔离组件没有的新失效模式？
- 关于集成的文档是最新的吗？

### 7. FEEL
- 这对用户来说感觉如何？（UX、错误信息、命名、上手摩擦）
- 用户碰到这个代码路径时处于什么情绪状态？（沮丧？探索？时间压力？）
- 即使数据说"我们没问题"，我的直觉说"有些不对劲"吗？
- 即使我无法明确说明原因，我的直觉说"我们没问题"吗？

### 8. ACCEPT
- 这个发现/ verdict 的诚实等级是什么？（不膨胀）
- 我被要求软化的什么约束是我不该软化的？
- 我在保护什么沉没成本是我该放手的？
- 如果这是别人的工作，我会更挑剔吗？

### 9. CREATE
- 能交付决策的最小程序是什么？
- 从这里到"完成"的最干净路径是什么？
- 输入足够了吗，还是我需要回环到更早的阶段？
- 交付它。

### 10. GROW
- 这个循环中什么做得好？
- 下次我会做什么不同？
- 什么输入喂养下一个版本？
- 这个教训应该存到哪里让未来的我不需要重新推导？（SKILL.md？架构文档？操作日志？）

## 与 KOS 引擎的映射

| 原则 | 相关 KOS 引擎 | 典型场景 |
|------|--------------|----------|
| OBSERVE | KOS-Triage、KOS-Compile | 读取源文件、扫描 Inbox |
| LISTEN | KOS-Triage | 从笔记中提取时间/动作信号 |
| THINK | 全部 | 四维分析、六步管道、五级检查 |
| CONNECT(lat) | KOS-Compile | 发现跨页面矛盾，标记 `conflict: true` |
| CONNECT(sys) | 全部 | 文件锁 → manifest → 日志的集成链 |
| FEEL | KOS-Triage | 无法路由时标记 `needs-mapping` 而非强塞 |
| ACCEPT | 全部 | 如实报告断链、矛盾、udc 缺失 |
| CREATE | 全部 | 写入文件、更新 manifest、生成报告 |
| GROW | 全部 | 操作日志、_logs/reports/、批次折叠 |

## 反模式

循环失败当：

- **跳过 OBSERVE(内)** — 从外部观察直接跳到 THINK，不审计自己的偏见，产生自信的错误答案
- **跳过 ACCEPT** — 膨胀评分、对冲 verdict、把 YELLOW 叫 GREEN。框架的防谄媚契约在 ACCEPT 变成可选时立刻死亡
- **跳过 GROW** — 产出工件、发布、然后继续前进而不反馈。下一轮从同样的第一性原理基线开始；没有东西复合
- **THINK 卡住** — 在第 4 阶段无限循环，永远到不了 CREATE。框架是一个序列，不是一个停止规则
- **仪式化** — 为单行修复写全部 10 个阶段。框架的成本应与问题的利害成正比

## 参数

- `/think <problem>` — 启动 10 原则思维循环
- `/think --quick <problem>` — 快速模式（跳过 2/7/8/10，聚焦 OBSERVE→THINK→CREATE）
- `/think --audit <topic>` — 审计模式（聚焦 OBSERVE→CONNECT→ACCEPT→GROW）
