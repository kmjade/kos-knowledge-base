# Project 生命周期操作手册

> 定位：AGENTS.md 约束"不能做什么"；本手册说明"怎么做"。
> 概念基础：ITO（Input → Transform → Output）目标流水线。

---

## 流程总览

```
验入法/隔离区/ ──→ 1-proposal/ ──→ 2-execution/ ──→ 3-completion/ ──→ 4-archived/
     ↑                ↑                 ↑                  ↑                ↑
  新想法           立项确认          工单执行            交付确认        物理归档
                                                                           ↓
                                                                    4 Archives/
                                                                           ↓
                                                                 0 Inbox/3-outcome/
```

**核心规则：** 项目必须完整走完四阶段。前三阶段有明确准入/准出条件。

---

## 各阶段操作

### 1-proposal/ — 论证中

| 属性 | 说明 |
|------|------|
| 含义 | Input — 资源投入前的决策 |
| 做什么 | 确认目标、优先级、资源、排期 |
| 输入源 | 验入法/隔离区/ 论证通过 |
| 预期时间 | ≤ 1 次会话 |

**准入条件：**
- [ ] 验入法七问论证通过
- [ ] 有明确的目标描述
- [ ] 有初步的交付物定义

**操作步骤：**

1. 从验入法/隔离区/ 获取论证通过的候选
2. 创建 `_提案.md` 文件，包含：
   - 目标与范围
   - 预估工作量（工单分解）
   - 资源需求
   - 截止日期
3. 分配 26-XX 项目编号（严格顺序递增，不跳过）
4. 确认立项后：创建项目目录，移入 `2-execution/`

**准出条件：**
- [ ] 目标/优先级/资源/排期已确认
- [ ] 项目编号已分配
- [ ] 项目目录已创建

### 2-execution/ — 执行中

| 属性 | 说明 |
|------|------|
| 含义 | Transform — 把输入转化为交付物 |
| 做什么 | 工单执行、进度跟踪、调整 |
| 输入源 | 1-proposal/ 立项确认 |
| 预期时间 | 取决于项目规模 |

**准入条件：**
- [ ] 从 1-proposal/ 移入
- [ ] 项目目录含 README 和工单清单

**操作步骤：**

1. 按工单清单执行
2. 每完成一个工单 → 标记 [x]
3. 过程中发现的知识 → 同步到知识库
4. 需要调整范围 → 更新项目 README
5. 产出完成 → 移入 `3-completion/`

**准出条件：**
- [ ] 所有工单全部完成（100% [x]）
- [ ] 交付物已产出

### 3-completion/ — 待结项

| 属性 | 说明 |
|------|------|
| 含义 | Output — 交付物完成 |
| 做什么 | 成果确认、Outcome 记录、结项报告 |
| 输入源 | 2-execution/ 产出完成 |
| 预期时间 | ≤ 1 次会话 |

**准入条件：**
- [ ] 从 2-execution/ 移入
- [ ] 工单全部完成

**操作步骤：**

1. 写 Outcome 摘要（实际影响、关键成果、可复用方法）
2. Outcome 摘要同步到 `0 Inbox/3-outcome/impacts/`
3. 写结项报告（完成度、验收标准、遗留事项）
4. 项目 frontmatter `status` 标记为 `completed`
5. 确认归档 → 移入 `4-archived/`

**准出条件：**
- [ ] Outcome 已记录到 `0 Inbox/3-outcome/`
- [ ] 结项报告已写入
- [ ] status: completed

### 4-archived/ — 已归档

| 属性 | 说明 |
|------|------|
| 含义 | 生命周期结束 |
| 做什么 | 物理移入 4 Archives/ |
| 输入源 | 3-completion/ 确认归档 |
| 预期时间 | ≤ 1 次操作 |

**准入条件：**
- [ ] 从 3-completion/ 移入
- [ ] 全部文件就绪

**操作步骤：**

1. 物理移动项目目录到 `4 Archives/`
2. 更新索引页引用
3. 确认 hot.md 等上下文文件不再引用旧路径

## 与 Inbox 交汇

两个流水线在 **3-outcome** 节点交汇：

```
Projects 侧                       Inbox 侧
─────────                        ─────────
3-completion/ 确认完成
    ↓
写 Outcome 摘要 ──────────────→ 存入 3-outcome/impacts/
    ↓
项目物理归档                     成果可被查询和引用
```

## 项目 vs 领域 边界

| 特征 | 项目（Projects） | 领域（Areas） |
|------|-----------------|---------------|
| 是否有截止日期 | 是 | 否 |
| 是否有明确交付物 | 是 | 不一定 |
| 执行方式 | 工单驱动，逐个完成 | 持续关注，定期回顾 |
| 生命周期 | 有限（四阶段） | 长期 |
| 示例 | 26-14 隐私加固 | 2 Areas/知识组织 |
| 归档方式 | 完成后移入 4 Archives/ | 不归档 |

**例外：** 26-02 Bug 追踪虽然持续，但作为"维护"放在 `2-execution/`，按项目方式管理工单。

## 常见场景

### 场景 1：一个新想法进来

```
验入法/隔离区/ 论证七问
    ↓ 通过
1-proposal/ 立项确认（编号 + 目标 + 排期）
    ↓ 确认
2-execution/ 执行工单
    ↓ 完成
3-completion/ 确认交付 + 写 Outcome → 0 Inbox/3-outcome/
    ↓ 归档
4-archived/ → 物理移入 4 Archives/
```

### 场景 2：项目中途需要调整范围

- 在项目 README 中更新目标和工单清单
- 移除或新增工单
- 不需要回到 1-proposal/（除非完全重定向）

### 场景 3：项目结论是不做了

- 在 3-completion/ 记录终止原因
- Outcome 记录为"终止：xxx"
- 仍然走完归档流程
