# 隔离区架构 全流程设计

> 从概念、架构、设计、开发、测试 全流程研讨隔离区（Quarantine Zone）设计方案

## 概念

解决三个缺口: P1无来源分级, P2无质量门禁, P3无去重。
隔离区回答"能入库吗？"（质量），Triage 回答"这是什么？"（主题）。
核心约束：不增新目录（frontmatter 状态机）、与 Triage 融合、幂等、非阻塞。

## 架构

管道: 收集端 → 0 Inbox/ → KOS-Triage + 隔离区三阶检查 → raw/ → Compile → wiki/
隔离区嵌入 Triage 引擎的最后三阶：门禁L0(元数据) → L1(完整性) → L2(去重) → L3(置信度)

## 设计

状态机: pending → scanning → cleared | rejected | escalated

L0元数据: source_type/captured_at/tags存在性检查，失败则自动修复
L1完整性: 长度>50字 + frontmatter闭合，失败则escalated
L2去重: 标题匹配/URL匹配/内容指纹，发现重复则rejected
L3置信度: 结合Triage四维分析结果，低分则escalated

永久路径：cleared → raw/, escalated → 标记待人工, rejected → 记录原因

## 开发

6步实现：
1. 定义隔离区frontmatter规范 → AGENTS.md
2. 修改Triage加入三阶门禁 → AGENTS.md
3. 定义来源溯源枚举表 → AGENTS.md
4. 修改路由逻辑 → AGENTS.md
5. 修改输出报告格式 → AGENTS.md
6. 迁移现有Inbox文件 → 3个文件
估算工作量: 40分钟

## 测试

7个测试场景: 正常/过短/无frontmatter/重复/低置信度/幂等/来源溯源
验收标准: Triage覆盖门禁、Inbox文件补齐、报告含隔离区块、AGENTS.md可执行

## 待定问题

- L2去重的扫描范围（全库 vs Inbox）
- rejected文件流向（删除 vs _rejected/归档）
- 与现有KOS-Triage的职责边界细节
- 移动端捕获的L0自动化
