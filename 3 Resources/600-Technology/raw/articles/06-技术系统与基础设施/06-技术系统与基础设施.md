# 06 技术系统与基础设施

> **UDC 6** —— 单个零件不难，难的是把**海量部件 · 子系统 · 人 · 规则**编成一台**可靠运行的系统**。
> 本章把视角从「**部件**」上升到「**系统**」与「**基础设施**」——连接 [[03-应用科学方法论|03 方法]] 与 [[05-标准化与规范导论|05 标准]] 的宏观层。

---

## 一、什么是技术系统

| 层级 | 说明 |
|:--|:--|
| **部件** | 单个器件（螺栓 · 芯片） |
| **子系统** | 部件 + 接口（发动机 · 电源模块） |
| **系统** | 完成一个功能（汽车 · 机床） |
| **系统之系统（SoS）** | 多个**独立系统**协同（电网 + 通信 + 交通） |

---

## 二、系统的性质

| 性质 | 含义 |
|:--|:--|
| **涌现** | 整体 > 部分之和（也会出**部分没有的故障**） |
| **接口 / 耦合** | 集成是风险高发区 —— **接口即协议** |
| **反馈与稳定** | 靠反馈维持目标（参见 [[007-控制论\|007 控制论]]） |
| **冗余与容错** | 冗余换可靠（代价是成本） |
| **瓶颈 / 最弱环** | 系统性能由**最弱一环**决定 |

---

## 三、系统工程（怎么设计系统）

```
需求 → 架构 → 分解 → 实现 → 集成 → 验证 → 确认   （V 模型）
```

- **需求跟踪**：每条需求可追到设计件与验证用例；
- **接口管理**：定义并**冻结**接口；
- **MBSE**：用模型承载需求—架构—验证闭环（替代文档堆）。

> 与 [[03-应用科学方法论|03 方法论]] 一致：**先定义对的需求，再分解、集成、验证**。

## 五、基础设施的特征

- **网络性**：节点 + 边；一处的波动会**传播**；
- **公共品 / 自然垄断**：边际成本低、覆盖成本高；
- **长周期 · 高沉没成本**：一建几十年，改造成本巨大；
- **路径依赖与锁定**：早期选择决定长期形态（参见 [[02-应用科学史与技术演化|02 史]]）；
- **脆弱性**：**级联失效**（一处倒，全网倒）。

---

## 六、韧性（Resilience）

| 手段 | 说明 |
|:--|:--|
| **冗余** | 备用路径 / 容量 |
| **多样** | 不依赖单一技术 / 供应商 |
| **分布** | 去中心，降低单点 |
| **可恢复** | 快速隔离 + 重建 |
| **演练** | 压力测试与预案 |

> 关键概念：**共模失效**（同一原因击穿所有冗余）· **级联**（故障沿网络放大）· **单点故障（SPOF）**。关键基础设施保护（CIP）即围绕此展开。

---

## 七、生命周期与运营

```
规划 → 设计 → 建设 → 运营 → 维护 → 更新 / 退役
```

> 系统的**寿命大头在运维**（几十年）；设计时就要为**维护可达性 · 备件 · 升级**留余地。基础设施尤其如此。

---

## 八、大型工程的教训

| 案例 | 教训 |
|:--|:--|
| 2003 美加大停电 | **级联失效**沿电网传播 |
| 切尔诺贝利 / 福岛 | 安全系统 + 组织 + 监管叠加失效 |
| 挑战者号 | 系统**耦合** + 组织**层级**压过安全 |
| 大坝 / 桥梁 | 单点结构失效 → 灾难 |

> 共同点：**系统级风险的来源，往往不在单个部件，而在接口 · 耦合 · 组织 · 与人。**

---

## 核心问题

**如何把海量部件、子系统与人，编成一个可靠、可持续、可演进的系统？**
