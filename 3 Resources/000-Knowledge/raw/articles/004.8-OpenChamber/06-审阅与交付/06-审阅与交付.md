# 06 审阅与交付

Agent 产出越快，人的瓶颈越从「写」转移到「读」。本章的三件事都围绕这个瓶颈：**把 diff 读成故事、把运行中的应用变成上下文、把交付流程收进同一个窗口**。

## Changes Walkthrough

### 它做什么

diff 默认按文件路径排序，而路径顺序几乎从不是理解顺序。Walkthrough 将其重组为 **stops（停靠点）**：

- 相关改动归为一组；
- 每个 stop 用一两句话解释「代码现在有什么不同」；
- stops 按**后一个建立在前一个之上**的顺序排列。

> 它只负责**解释与排序**，不评判代码好坏。判断质量是 **Review** 的职责。

### 启动

- 右栏 **Walkthrough** 图标；
- Changes / Pull Request 面板的 **AI walkthrough** 按钮。

两者都只打开面板；**不按 Generate 就不会生成**。

### stop 标签

| 标签 | 含义 |
|------|------|
| **Key change** | 驱动其余改动或承载主要风险，应先读、细读 |
| **Context** | 支撑性改动，用于理解上下文，可略读 |
| （无标签） | 普通步骤 |

> 标签标记的是**注意力该放哪**，不是代码质量。Walkthrough 不输出 findings、severity 或 verdict。

### 审阅范围

| 范围 | 覆盖内容 |
|------|---------|
| All uncommitted | 已暂存 + 未暂存 + 新文件 |
| Staged | 即将进入本次提交的内容 |
| Unstaged | 工作区与新文件 |
| This branch | 本分支相对 base 的**全部提交**（含已推送） |
| Pull request | GitHub 上该 PR 的现状 |

> **This branch** 不等于「未推送提交」；提交后未推送时，它与 PR 视图刻意不同——一个是你做了什么，一个是评审者看到什么。各范围分别存储，切换不丢失。

### 模型与语言

| 项 | 规则 |
|----|------|
| 默认模型 | 小模型（Settings → Sessions → Changes Walkthrough Model 可改） |
| 单次覆盖 | 面板头部可为高风险改动换更强模型 |
| 能力门槛 | 仅提供**能返回结构化输出**的模型 |
| 过小模型 | 直接拒绝并说明原因，**不静默截断**——半份 diff 生成的导览会「自信地错」 |
| 语言 | 默认跟随界面语言，可按次切换；**只翻译叙述**，标识符、路径、API 名保持原样 |

### 成本与缓存

- 不会自动生成，重新生成也需手动；
- 结果按 **diff 精确内容** 缓存：工作树回到旧状态，旧导览免费取回；
- 语言与模型都是缓存键的一部分；
- 生成在**服务端**运行，关页面不影响；只有 **Cancel** 会停止。

### 陈旧检测

| 标记 | 含义 |
|------|------|
| **Outdated** | stop 描述的代码已变化或消失；导览仍显示但被标记 |
| **Not covered** | 当前 diff 中没有任何 stop 描述的改动（含生成后的编辑、被判为常规的改动、lockfile 等生成文件） |

重新生成是**重写而非补丁**：旧导览作为上下文传入，准确部分得以保留，全部重新锚定到当前代码。

### 限制

- 桌面与平板宽度可用；**VS Code 扩展与移动端不提供**；
- PR 审阅需先连接 GitHub 账号；
- 可在任意行评论，评论进入 chat composer。

## Preview 与 dev server

### 打开方式

- 应用头部的**地球按钮**打开浏览器面板；
- 若已有 dev server 在运行，会直接列出——通过探测本机实际监听端口发现，**不关心你是怎么启动的**；
- 自动打开：终端里点 **Open preview**、启用自动打开的项目动作启动服务、点击聊天里的本地链接。

> 直接输入 `localhost:5173` 会按 `http://` 处理。

### 远程实例

当 OpenChamber 跑在另一台机器上，dev server 也在那台机器：

- **桌面应用**会建立本地端口转发，页面正常加载，热更新与开发者工具可用；
- **纯浏览器**只能打开本机 dev server。

### 标注与 Browser Use

在浏览器面板中：

- 指向元素 → 发送截图、样式、位置、浏览器错误；
- 可在页面上绘制标注；
- agent 也能点击页面、查看报错并检查自己的工作。

## GitHub / Linear 集成

### 连接 GitHub

1. Settings → Integrations → **GitHub**；
2. **Connect GitHub**，打开链接并输入短码；
3. 授权完成。

支持多个账号切换；若本机 `gh` CLI 已登录，可作为回退。

### 从 issue / PR 开始

在**worktree 会话**中：

| 起点 | 行为 |
|------|------|
| Issue | 分支按 issue 命名 |
| Pull request | 检出该 PR 分支；可选择附带 PR diff，让 agent 拿到完整改动 |

新会话打开时条目已附加到消息框，但**不会自动发送**——选好模型与 agent，写清要做什么，再发送。

### 交付

- Git 视图的 **PR** 标签页：创建、更新、草稿转正、合并；
- 可由改动生成 PR 标题与描述；
- 聊天 composer 的 **+** 菜单可附加一个或多个 issue/PR 作为上下文（PR 可带 diff）。

### 集成覆盖

| 平台 | 状态 |
|------|------|
| GitHub | 已支持 |
| Linear | 已支持 |
| GitLab | 开发中 |

## 交付闭环

```
开始（issue / 目标 / 计划）
   ↓
运行（Multi-run / Fusion / Browser Use）
   ↓
审阅（Walkthrough / Preview 标注 / 失败 CI 回传）
   ↓
提交 · 推送 · 开 PR · 回复评审 · 合并（同一窗口）
```

> 设计意图：**不离开工作发生的窗口**。
