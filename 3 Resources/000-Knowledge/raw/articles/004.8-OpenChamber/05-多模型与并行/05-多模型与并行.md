# 05 多模型与并行

## 为什么需要并行

单模型单次生成是一个**赌注**：选对模型、一次写对。Multi-run 把这个赌注改成**采样**——同一任务交给多个模型，各自独立完成，再由人择优或合成。

适用场景：

- 同一需求想比较不同模型的实际产出；
- 高风险改动需要多条独立路径；
- 探索性重构，不确定哪种方案更好。

## Multi-run

### 启动

两个入口：

- composer 的模型选择器 → **Run on several models**
- 命令面板 → **Run in parallel**

### 五步流程

1. 选择项目；
2. 为本次运行组命名；
3. 写提示词；
4. 选择参与的模型；
5. 决定是否 **isolate runs**（隔离运行）；
6. 启动。

每个模型获得**独立会话**，均以同一提示词开始。

### 隔离运行（Isolate runs）

| 选项 | 行为 | 前提 |
|------|------|------|
| 开启 | 每个 run 拥有**独立 git worktree 与分支**，互不接触文件 | 需要 git 仓库；非 git 文件夹自动关闭 |
| 关闭 | 每个 run 只是项目文件夹里的普通会话 | 无 |

开启时可选择所有 run 的**起始分支**。

### 结果处理

- 每个 run 都是普通会话：可打开、阅读、保留或丢弃；
- 可并排审阅，把最好的一个继续推进；
- **部分失败不影响其余**：某个 run 启动失败，其他仍会启动，只是会话数变少。

### 数量上限

| 来源 | 表述 |
|------|------|
| README | 最多 **5 个模型** |
| 官方文档 | "several models"（未给数字） |

> 以实际界面为准；文档未固定上限，可能随版本调整。

## Worktree 会话

Multi-run 的隔离依赖 **git worktree**。单独使用时：

| 步骤 | 说明 |
|------|------|
| 创建 | 分支菜单 **New worktree…**，或项目行的 worktree 按钮；**Quick worktree** 可跳过命名 |
| 起点 | 新分支 / 已有分支 / PR 或 issue（分支自动命名，条目附加到首条消息） |
| 参数 | **Based on**（新分支的基点，默认项目当前分支）、**Folder name** |
| 初始化 | 若项目配置了 setup commands，创建后自动执行 |
| 回收 | **Integrate** 把 worktree 提交合回目标分支；冲突可交给 agent 解决 |
| 清理 | 删除/归档会话时可移除 worktree；是否删分支（本地与远端）由你决定 |

> 设计原则：**不询问就不删除**。

## Fusion

README 的描述：把多个 run 中**最强的部分合成一个新会话**。

| 项 | 状态 |
|----|------|
| 定位 | 从「择优」走向「合成」 |
| 实现细节 | 官方文档尚未提供独立页面，机制未公开 |
| 可信度 | 产品自述，未经第三方验证 |

> 与 Multi-run 的区别：Multi-run 产出多个完整候选；Fusion 试图产出**一个更优的合成结果**，代价是可解释性下降。

## 工程判断

| 维度 | 收益 | 风险 |
|------|------|------|
| 并行采样 | 提高一次命中的概率；便于横向比较 | token 成本线性上升 |
| worktree 隔离 | 避免并行写冲突；保留可回滚的分支 | 仓库体积与清理成本 |
| 结果择优 | 人保留最终判断权 | 审阅负担增加 |
| Fusion | 可能兼取各家之长 | 合并逻辑不透明，难以归因 |

## 实践建议

1. **先隔离再并行**——不开 worktree 的 Multi-run 只适合只读任务（分析、方案讨论）。
2. **控制模型组合**——2–3 个差异明显的模型比 5 个同源模型更有信息量。
3. **给 run group 起名**——否则并行会话很快难以辨认。
4. **把 Fusion 当实验特性**——在关键路径上仍以人工择优为主。
